# pi-observer: Claude наблюдает, pi работает

Скрипты: `~/.claude/skills/pi-observer/scripts/`
- `pi-start <workdir> <phase.md> [model] [timeout]` — запустить фазу (новая сессия); печатает `SESSION=`, `OUT=`; пишет `.pi_runs`.
- `pi-start <workdir> --continue <session-id> <msg.md> [model] [timeout]` — дописать в ту же сессию (исправление, следующий шаг).
- `pi-check <workdir> [session-id]` — **механическая приёмка за 5–15 строк**: работает ли pi, PI-EXIT,
  ошибки (и шли ли вызовы после них), «ГОТОВО» поверх ошибок, повторы падающей команды, опасные
  действия (публикации, task_close/stand_destroy, .poligon_claim, файлы контролёра), «Poligon» в
  черновиках, утечки секретов (значения не печатает), обновлён ли PROGRESS. Код: 0 OK, 1 замечания, 3 работает.
- `pi-log <session-id|file> [--from N] [--brief | --full]` — лента сессии. `--brief`: только команды и коды;
  `--full --from N`: полный вывод с события N. Секреты из `creds*.sh` и ключи из окружения маскируются.
- `pi-watch [корни]` — TUI для человека (задачи, живая лента pi, PROGRESS.md, стенды; s/c/k). Claude его
  не запускает (интерактивный) — предлагает пользователю открыть в соседнем терминале.
  Пометка задачи ⚠ = в последней сессии есть ERROR/rc≠0 — первый кандидат на проверку.

Исполнитель по умолчанию: `basealt/qwen3.8-27b` (локальная модель, контекст и внимательность ограничены —
фазы должны быть короткими и однозначными). Скиллы `poligon-*` у pi лежат в `~/.pi/agent/skills/`,
к Poligon он ходит через CLI `poligon-call` / `poligon-run` (claim из `./.poligon_claim`).
Шаблон общей инструкции исполнителю: `~/compat/PI_PROMPT.md`.

## Роли — жёстко

**pi делает:** все вызовы, меняющие стенды и задачи (`task_create`, `stand_apply`, `stand_exec`,
`poligon-run`, `stand_power`, `finding_add`), пишет скрипты, `PROGRESS.md`, черновики отчётов.

**Claude делает:** план и тексты фаз (`phaseX.md`), запуск pi, наблюдение, независимая проверка,
решение «принять фазу / вернуть на доработку / стоп и к пользователю», итоговое резюме пользователю.
Claude **не** чинит работу pi руками на стенде и не правит его скрипты — возвращает фазу с
конкретным замечанием. Исключения — только с согласия пользователя (секреты, как ключ ППО в
`run_all.sh`, контролёр кладёт сам, чтобы они не попали в контекст и логи pi).

**Только по явному «да» пользователя** (не по своему решению и не по слову pi):
публикация в Redmine/TestLink, `task_close`, `stand_destroy`, выгрузка в Nextcloud.

Проверочные вызовы Claude — только читающие (`poligon-call` из каталога задачи, там `.poligon_claim`):
`stand_status`, `stand_wait` (seconds ≤ 50), `task_get`, `task_list`, `finding_list`,
`calls_export` (серверный журнал вызовов задачи — сверка с тем, что pi заявляет), `stand_file_get`
(чтение логов на ВМ), `stand_screenshot`/`stand_console_read`, `stand_exec` только с командами вида
`cat`/`systemctl status`/`rpm -q`/`journalctl`; плюс alt-rdb / alt-bugzilla / alt-gitoskop. Сверяйся с `poligon-common` и `poligon-troubleshooting`
(в `~/.claude/skills/`), прежде чем объявлять поведение инструмента ошибкой.

## Цикл

### 1. Подготовка (Claude)
- Каталог задачи (`~/compat/<N>` для техсовместимости, иначе `~/poligon/<id>`); прочитать
  `PROGRESS.md`, `.pi_runs`, прошлые `phase*.md` — продолжаем, а не начинаем заново.
- Собрать вход из первоисточников (alt-rdb/girar, Bugzilla, Redmine-JSON, TestLink-выжимка pi)
  и соответствующий скилл `poligon-*` — по нему разбить работу на фазы.
- Фаза = 3–8 конкретных шагов с проверяемым результатом. В тексте фазы:
  контекст (задача, стенд, роль), шаги нумерованно, **критерий готовности каждого шага**
  (маркер в выводе, rc), что делать при ошибке («стоп и дословно в PROGRESS» — по умолчанию;
  «продолжай» — только если шаг независим), запреты (`.poligon_claim`, файлы контролёра,
  публикации, обходы), формат итога (строка в `PROGRESS.md` + слово `ГОТОВО`).
- Если параметры инструментов не очевидны — сначала `poligon-call schema <tool>` и вписать
  лимиты в фазу (пример промаха: `stand_wait seconds` ≤ 50, а фаза просила 90).
- Показать пользователю план фаз один раз перед первым запуском; дальше идти без вопросов,
  кроме гейтов публикации/удаления и стоп-ситуаций.

### 2. Запуск (Claude)
Запускать в фоне: Bash `run_in_background: true` с
`~/.claude/skills/pi-observer/scripts/pi-start <dir> phaseA.md`. Из первой строки вывода взять `SESSION`.

### 3. Ожидание — без опроса (экономия токенов)
- Не опрашивать pi во время фазы: о завершении фонового `pi-start` придёт уведомление, тогда — приёмка.
  Пользователь при желании смотрит ход в `pi-watch`.
- Только для очень долгих фаз (> 30 мин): одна контрольная точка `pi-check <dir>` не чаще раза
  в 20–30 мин (ScheduleWakeup/отложенная проверка), не `pi-log` целиком.
- Вмешиваться **до** завершения, только если `pi-check` показал явный вред: опасное действие,
  правка `.poligon_claim`/файлов контролёра, повтор падающей команды ≥3. Остановка pi
  (процесс называется `pi`, искать по каталогу):
  `for p in $(pgrep -x pi); do [ "$(readlink /proc/$p/cwd)" = "<dir>" ] && kill $p; done`
  → запись в PROGRESS → пользователю.

### 4. Приёмка фазы (главное)
Не верить итоговому тексту pi. Порядок — от дешёвого к дорогому:
1. **`pi-check <dir>`** — всегда первым. Вердикт OK и нет сомнений по сути фазы → сразу к п.4.
2. Есть замечания → `pi-log <SID> --brief` (весь ход фазы коротко), затем `--full --from N`
   только по событиям из замечаний. Целиком `--full` не читать.
3. По существу (то, что скрипт не видит): все ли шаги фазы вызваны и в нужном порядке; не зависел
   ли следующий шаг от «проглоченной» ошибки; «OK» в PROGRESS/отчёте подтверждено маркером
   `*-DONE`/`rc=0`; при сомнениях — `calls_export` по задаче (что реально дошло до сервера).
4. Одна выборочная независимая проверка на стенде читающей командой (сервис активен, пакет нужной
   версии, лог без ошибок) — по ключевому факту фазы. Вывод ограничивать (`| tail -20`, `--max 1500`).
5. Красные флаги из `PI_PROMPT.md` и скилла `poligon-*`, которые pi-check не ловит: пробелы в путях,
   podman без `default_subnet`, нет md5sum, расширение живого стенда.
6. `pi-check` нашёл СЕКРЕТ → сообщить пользователю, где именно (имя файла), значение не открывать.

Решение:
- **Принято** → строка `КОНТРОЛЬ <дата> | phaseX принята | <основание>` в `PROGRESS.md`, следующая фаза.
- **На доработку** → `phaseX-fix1.md` с конкретикой («шаг 4 упал: `seconds must be in 0..=50`;
  повтори stand_wait 2×45 с, затем `stand_exec uptime`; func2 перезапусти после этого»),
  `pi-start ... --continue <SID> phaseX-fix1.md`. Две неудачные доработки подряд — к пользователю.
- **Стоп** → ошибка инфраструктуры/доступов/ресурсов, неясность в требованиях, расхождение
  с ТЗ — дословно пользователю, с предложением вариантов.

### 5. Финал
- Проверить черновики pi (`report.md`, `tl_results.md`, `redmine_comment.md`) против ленты
  сессий: каждый результат кейса pass/fail/blocked подтверждён выводом; блокеры есть в findings.
- Пользователю: таблица кейсов с результатами и ссылками на доказательства (файл лога/событие
  сессии), найденные проблемы исполнителя и что было исправлено, ресурсы/время, открытые гейты
  («публиковать в TestLink? удалить стенд?»). Публиковать — только после явного ответа.

## Разбор чужой/прошлой сессии (`review <session-id>`)
Только шаги 4 и 5 по готовой сессии: `pi-check <dir> <SID>`, затем `pi-log <SID> --brief` и
`--full --from N` по замечаниям; сверка с `PROGRESS.md` и файлами каталога, список расхождений
с номерами событий `#N`.
